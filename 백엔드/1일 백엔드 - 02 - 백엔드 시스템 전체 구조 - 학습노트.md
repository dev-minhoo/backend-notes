# 1. 기초 — 프로세스 · JVM · 서버

## 1-1. 프로그램 vs 프로세스

```
프로그램 = 디스크에 저장된 파일 (죽어있음)     예) app.jar
프로세스 = 그 파일이 메모리에 올라가 실행 중    (살아있음)
```

같은 프로그램이 프로세스 여러 개가 될 수 있다. (크롬 아이콘 = 프로그램 / 크롬 창 3개 = 프로세스 3개)
`java -jar app.jar` = **디스크의 파일이 메모리로 올라가 프로세스가 되는 순간.**

## 1-2. JVM이란

**문제**: C는 CPU가 직접 알아듣는 기계어로 컴파일된다. 그런데 기계어는 OS·CPU마다 다르다.

**Java의 해법**
```
.java → 컴파일 → 바이트코드(.class) → [ JVM ] → OS → CPU
                  CPU가 못 알아듣는       ↑
                     중간 언어         OS별 통역사
```

앱은 그대로 두고 **JVM만 OS에 맞는 걸 깔면 된다.** ("Write Once, Run Anywhere")

**`java -jar app.jar`가 실제로 하는 일**
1. JVM 프로세스를 하나 띄운다
2. 그 JVM 안으로 app.jar를 올린다
3. `main()`을 실행한다

→ **프로세스의 정체는 사실 JVM이고, 내 앱은 그 안에서 돈다.**

**JVM은 통역만 하지 않는다**

| 역할 | 내용 |
|---|---|
| 바이트코드 실행 | 통역 + JIT 컴파일(자주 쓰는 부분은 기계어로 캐싱) |
| **메모리 관리** | Heap 할당, **GC** — C처럼 `free()` 안 해도 되는 이유 |
| 스레드 관리 | OS 스레드와 매핑 |
| 클래스 로딩 | 필요할 때 `.class`를 메모리로 |

> "GC 튜닝 해봤나"(`-Xmx`, GC 종류 선택) 같은 질문이 이 층 이야기.

## 1-3. 서버 프로세스란

```
일반 프로그램: 시작 → 할 일 → 끝 → 종료
서버 프로그램: 시작 → 포트 열고 → 무한 대기 → 요청 처리 → 다시 대기 (안 끝남)
```

**포트 = 한 컴퓨터 안에서 프로그램을 구분하는 번호 (0~65535).** IP는 건물 주소, 포트는 호실.

```
:8080  Spring Boot     :3306  MySQL
:9092  Kafka           :6379  Redis
:5672  RabbitMQ
```

"포트 충돌" 에러 = 이미 누가 쓰는 번호를 또 열려고 할 때.

## 1-4. 실제 서버에서 (`ps -ef`)

```
1234   java -jar rootinfra-api.jar     ← Spring Boot (JVM 프로세스)
5678   /usr/sbin/mysqld                ← MySQL (C, 네이티브)
9012   nginx: master process           ← 웹서버
3456   java -jar kafka_2.13-3.7.0.jar  ← Kafka도 JVM 프로세스!
```

> 💡 **Kafka가 Java라는 사실이 여기서 실체가 된다.** 그 서버에 JDK가 필요하고, **GC 문제가 생길 수 있다.**
> Kafka 운영에서 힙 튜닝이 이슈가 되는 이유 = "Kafka는 운영이 무겁다"의 실체 중 하나.

## 1-5. 배포 형태

| 형태 | 설명 |
|---|---|
| 한 서버에 다 몰기 | 개발·소규모 |
| 서버 분리 | 앱/DB/Kafka 각각 별도 장비 |
| **Docker** | 프로세스를 격리 상자에 담아 실행. `docker run` 한 줄 |
| Kubernetes | 컨테이너를 여러 대에 자동 배치·재시작 |

**Docker가 편한 이유**: Kafka 직접 설치는 JDK 설치 → 압축 해제 → 설정 파일 수정… `docker compose up -d` 한 줄이면 끝.
→ **8월 Redis 실습, `payment-settlement-core` 모두 이 방식으로 진행.**

# 2. 진입 계층

## DNS
`www.example.com` → IP. 사람은 IP를 못 외우고, **서버를 바꿔도 도메인은 유지**할 수 있다.
> 실무 함정: TTL(캐시 유지 시간) 때문에 서버 이전 후에도 일부 사용자가 옛 서버로 간다.

## CDN
이미지·CSS·JS를 전 세계 캐시 서버에서 제공.
**없으면**: 부산 사용자가 이미지 하나에 서울까지 왕복. 느리고 서버 트래픽 폭증.
> 6년차 포인트: **캐시 무효화.** 파일을 바꿨는데 CDN에 옛 버전이 남는다 → 파일명에 해시(`app.a3f9.js`).

## 로드밸런서 / Nginx — 규모 확장의 출발점

```
서버 1대:      요청 1만개 → 💥
서버 3대 + LB: 3,333개씩 분배 → 버팀 + 1대 죽어도 헬스체크로 자동 제외
```

| 역할 | 설명 |
|---|---|
| 트래픽 분배 | 라운드로빈, 최소 연결 등 |
| 헬스체크 | 죽은 서버 자동 제외 → 사용자는 장애를 모름 |
| SSL 종료 | HTTPS 복호화를 여기서. 뒷단은 HTTP |
| 정적 파일 | 이미지·JS는 Nginx가 직접 응답. WAS까지 안 감 |

### ★ 여기서 나오는 핵심 개념 — 무상태(Stateless)

```
로그인 → 서버1 메모리에 세션 저장
다음 요청 → LB가 서버2로 보냄 → "로그인 안 하셨는데요?"  💥
```

**세션을 서버 메모리에 두면 스케일아웃이 불가능하다.**

해결: **Redis에 세션 저장**(서버 밖으로) 또는 **JWT**(서버가 세션을 안 가짐)

> 💡 **"왜 Redis를 쓰나요"의 1번 답은 캐시가 아니라 이것.** 세션 외부화 = 스케일아웃의 전제 조건.

# 3. 애플리케이션 계층

## 3-1. WAS 내부

Spring Boot = **내장 Tomcat이 8080을 열고 무한 대기하는 JVM 프로세스.**

```
요청 도착 → Tomcat 스레드풀(기본 200)에서 스레드 1개 배정
        → 그 스레드가 내 코드 실행 → 응답 후 반납
```

> 💡 **스레드풀 200 vs 커넥션풀 10 불일치** 문제가 정확히 이 지점.
> 스레드 200개가 커넥션 10개를 기다리며 쌓인다 → 지표 `hikaricp_connections_pending`

## 3-2. 계층 구조 — 왜 나누나

```
[ Controller ]  HTTP를 아는 층. 요청 파싱 · 응답 형태 · 상태코드
      ▼
[ Service ]     업무 규칙. 트랜잭션 경계가 여기          ← 핵심
      ▼
[ Repository ]  DB 접근만
      ▼
[ Domain ]      데이터와 규칙 자체
```

**한 문장**: **바뀌는 이유가 다른 것들을 분리한다.**

- API 응답 형식 변경 → Controller만
- MySQL → PostgreSQL 교체 → Repository만
- 업무 규칙 변경 → Service만

**안 나누면**: Controller에 SQL과 업무 로직이 뒤엉킨다 → 배치에서 재사용하려면 복붙, 테스트하려면 HTTP 요청을 만들어야 함.

> 💡 **Hexagonal Port & Adapter**(현 SaaS 프로젝트)는 이걸 더 밀어붙인 형태.
> "외부 세계(DB·API·SMS·PG)는 전부 Adapter로 갈아끼울 수 있게" — 방향은 같고 경계가 더 명확할 뿐.

## 3-3. 횡단 관심사 (AOP)

로깅·인증·트랜잭션처럼 **모든 층에 걸친 것**. 각 메서드에 다 쓰면 코드가 오염되니 뽑아낸다.
`@Transactional`이 대표. → **프록시 기반**이라 self-invocation·private·final에서 안 걸린다.

# 4. 데이터 계층

## 4-1. DB — 진짜 정답이 사는 곳

나머지(캐시·검색엔진·분석DB)는 전부 사본이거나 임시다.

| 6년차가 알아야 할 것 | 왜 |
|---|---|
| 인덱스 원리, `EXPLAIN` | 느린 쿼리의 90% |
| 트랜잭션 격리 수준 | 팬텀리드·논리피터블리드 |
| 락 (공유/배타, `FOR UPDATE`) | **금융 필수** |
| 커넥션 풀 | 점유 시간 = 고갈의 본질 |
| **Master/Slave 복제** | 읽기 부하 분산 |

> ⚠️ **복제 지연 함정**
> 쓰기는 Master, 읽기는 Slave로 보내면 — 방금 저장한 데이터를 조회할 때 **아직 복제 전이라 없다고 나온다.**
> "저장했는데 목록에 안 보여요" 버그의 정체. 해결: 쓰기 직후 조회는 Master로 강제.

## 4-2. 캐시 (Redis)

```
조회 → Redis에 있나?  있으면 반환 (0.1ms)
              없으면 → DB 조회 (10ms) → Redis 저장 → 반환
```

**Redis의 실제 용도 5가지 (8월 학습 범위)**

| 용도 | 설명 |
|---|---|
| **세션 저장소** | 스케일아웃의 전제 |
| **캐시** | 조회 결과 임시 저장 |
| **분산 락** | 여러 서버가 같은 작업을 동시에 못 하게 |
| **멱등성 키 저장** | 중복 요청 차단 (TTL 활용) |
| **큐 (Stream)** | 노트 01 참조 |

**6년차 필수 — 캐시 3대 문제**

- **캐시 스탬피드** — 캐시 만료 순간 수천 요청이 동시에 DB로 몰림
- **캐시 무효화** — DB는 바뀌었는데 캐시는 옛 값. 어디서 지울지가 어렵다
- **캐시 침투** — 없는 키를 계속 조회 → 매번 DB까지 감

> `payment-settlement-core`의 **멱등성 키 + TTL**, **분산 락**이 이 계층 이야기.

## 4-3. 파일 저장소 (S3)

이미지·PDF를 **DB에 넣으면** 백업이 무거워지고 DB 부하가 커진다.
**서버 로컬 디스크에 넣으면** 서버가 3대일 때 파일이 어디 있는지 모른다.

# 5. 비동기 계층

**"동기 요청 경로에서 빼낸 것들이 사는 곳."**

```
[사용자 요청]  ← 여기는 1초 안
      ├─ 꼭 지금 해야 하는 것 → 동기
      └─ 늦어도 되는 것       → 큐
                    ┌────────┼────────┐
                [소비자]  [소비자]   [배치]
```

## 큐 vs 배치 — 구분이 중요

| | 트리거 | 처리 단위 | 예 |
|---|---|---|---|
| **메시지 큐** | **이벤트 발생 시** | 건별, 흘려보냄 | 상환 완료 → 알림 |
| **배치** | **정해진 시각** | 덩어리로 모아서 | 새벽 2시 정산 대사 |

> ⚠️ **내 NH 대량이체는 배치형이다.** 면접에서 "큐를 써봤나"에 이걸 큐라고 하면 안 된다.
> **"배치로 처리했고, 큐와의 차이는 트리거와 지연 특성"** 으로 구분해서 말할 것.

## 대사(Reconciliation) — 금융의 핵심

```
매일 새벽: 우리 DB의 이체 내역  vs  은행이 준 거래 내역
        → 안 맞는 건 찾아 보정
```

**비동기·분산 시스템은 반드시 틀어진다.** 그래서 **"틀어진 걸 찾아내는 배치"가 별도로 존재**한다.
이게 있어야 at-least-once나 보상 트랜잭션을 실무에서 감당할 수 있다.

> `payment-settlement-core`에 대사 배치를 넣는 이유. **결제 회사 면접에서 가장 크게 먹히는 항목.**

# 6. 외부 연동 계층

NH 오픈뱅킹·금결원·PG·알림톡 — **통제할 수 없는 것들.**

**방어 장치 5개**

| 장치 | 문제 | 해결 |
|---|---|---|
| **타임아웃** | 응답이 안 오면 스레드가 영원히 묶임 | connect/read 타임아웃 필수 |
| **재시도 + 백오프** | 일시적 오류 | 1초→2초→4초 |
| **멱등성 키** | 재시도가 중복 실행 | ✅ **경험 있음** (금결원 거래고유번호) |
| **서킷 브레이커** | 죽은 API를 계속 때림 | 실패율 초과 시 차단, 주기적 재시도 |
| **보상 트랜잭션** | 되돌릴 수 없는 외부 호출 후 실패 | ✅ **경험 있음** (양도양수) |

> 💡 **내 강점이 정확히 이 칸에 있다.** 3·5번을 실무로 해본 사람은 흔치 않다.
> 문제는 "이게 지도의 어느 칸인지" 말해본 적이 없었다는 것뿐.

# 7. 운영 계층

프로세스가 여러 개로 흩어진 순간 생기는 문제들.

| | 왜 필요 |
|---|---|
| **로그 수집** (ELK, Loki) | 서버 3대면 로그도 3곳. 한 곳에 모아야 검색 가능 |
| **분산 추적 (Trace ID)** | **비동기로 쪼개면 호출 스택이 끊긴다.** 요청마다 ID 부여해 전 구간 추적 |
| **메트릭** (Prometheus + Grafana) | 커넥션 풀 사용량, 큐 적체(lag), 응답시간 |
| **알림** | 큐가 1만 건 밀리면 새벽에 깨워야 함 |
| **CI/CD** | 푸시 → 자동 빌드·테스트·배포 |

> ⚠️ **Trace ID는 큐를 도입하면 필수가 된다.**
> "큐의 대가 — 디버깅 난이도"의 실체. 요청 하나가 3개 소비자로 흩어지면 공통 ID 없이는 추적 불가.

# 8. 연차별 이해 범위

| 영역 | 신입~2년 | 3~5년 | **6년차 기준선** |
|---|---|---|---|
| 계층 구조 | 나눠서 짬 | 왜 나누는지 설명 | **경계를 직접 설계.** 선택 근거 |
| DB | CRUD, JOIN | 인덱스, 실행계획 | **락·격리수준·복제지연.** 풀 튜닝 |
| 트랜잭션 | `@Transactional` 붙임 | 전파 속성 이해 | **경계를 어디서 자를지 판단** |
| 캐시 | 개념 | Redis 조회 캐싱 | **무효화 전략·스탬피드·분산 락** |
| 비동기 | `@Async` | 큐 개념 | **유실·중복·순서·재처리 설계.** 도구 선택 근거 |
| 외부 연동 | API 호출 | 재시도 | **타임아웃·서킷·멱등성·보상** |
| 확장 | 모름 | 스케일아웃 개념 | **무상태 설계, 병목 예측** |
| 운영 | 로그 봄 | 지표 봄 | **장애 시 원인 계층을 좁혀 들어감** |
| **판단력** | "된다/안 된다" | "이게 낫다" | **"이 규모엔 A, 커지면 B. 트레이드오프는 이것"** |

> **맨 아랫줄이 6년차와 3년차를 가르는 진짜 기준.**
> 기대되는 건 최신 기술 지식이 아니라 **"왜 그걸 안 쓰기로 했는지 설명할 수 있는가"**.

# 9. 현재 위치 진단

## 이미 6년차 수준
- **외부 연동 방어** (멱등성·보상·부분 실패) — 상위권
- **트랜잭션 정합성 설계**
- **레거시 결함 추적·재설계** (양도양수)
- **도메인 모델링** (멀티테넌시, 권한 매트릭스)

## 3년차 수준에 머물러 있는 것
- **확장(scale) 관점** — 서버 여러 대 전제의 설계 경험 없음
- **캐시** — 개념만
- **비동기 인프라** — `@Async` 수준
- **운영 관측** — 지표 기반 장애 대응 경험 부족

## 진단 한 줄

> **"깊이는 있는데, 그 깊이가 지도의 어느 칸인지 설명해본 적이 없다."**

서류 5건 전부 컷된 것과 무관하지 않다. 개별 성과는 강한데
**"시스템 전체에서 내가 어느 부분을 책임졌는가"** 로 보이지 않았다.

## 8~10월이 메우는 칸

| 학습 | 채우는 칸 |
|---|---|
| **8월 Redis** | 캐시 계층 + 분산 락(다중 서버 전제) + 멱등성 저장 |
| **9월 Kafka** | 비동기 계층 전체 |
| **`payment-settlement-core`** | **위 칸들을 하나로 연결** — 큐·캐시·배치·보상이 한 프로젝트에 |

→ 이 프로젝트는 이력서 한 줄이 아니라 **지도 자체를 채우는 작업**이다.

# 오늘 남길 3줄

1. 시스템은 **진입 → 앱 → 데이터 → 비동기 → 외부 → 운영** 6계층이고, 전부 **별개 프로세스가 네트워크로 대화**한다
2. 각 구성요소는 **"없으면 뭐가 깨지는가"** 로 이해한다
   (LB 없으면 확장 불가 · Redis 없으면 세션 때문에 스케일아웃 불가 · 큐 없으면 장애 전파)
3. 6년차 기준은 지식량이 아니라 **선택의 근거와 트레이드오프를 말할 수 있는가**
