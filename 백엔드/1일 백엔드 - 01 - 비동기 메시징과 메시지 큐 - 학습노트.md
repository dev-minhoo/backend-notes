# 블록 0. 큐가 왜 나왔나 — 출발점

**상황**: 사용자가 "일괄 상환" 버튼을 누르면 뒤에서 할 일이 5개다.

```
① 상환 대상 조회
② NH 오픈뱅킹 출금이체 호출   ← 3초
③ 상환 내역 DB 기록
④ 투자자에게 알림톡 발송      ← 2초
⑤ 정산 데이터 집계            ← 1초
```

동기로 다 하면 **사용자가 6초를 기다린다.**
더 나쁜 건, **알림톡 서버가 죽으면 ④에서 예외가 터져 이미 성공한 이체(②)까지 실패로 처리**된다. 돈은 나갔는데 화면엔 실패.

> **여기서 나온 두 문장이 메시지 큐 존재 이유의 전부다.**
> 1. "알림톡 발송을 사용자가 왜 기다려야 하지?"
> 2. "알림톡 서버가 죽었다고 왜 이체가 실패로 보이지?"

**해법 = 쪽지함을 하나 둔다**

```
[상환 처리] ──이벤트 발행──▶ 📮 브로커 ──▶ [알림톡 소비자]
      ↑                              └──▶ [정산 소비자]
 사용자에게 즉시 응답
```

- 사용자 응답 1초 (**응답 시간 개선**)
- 알림톡 서버가 죽어도 이벤트는 브로커에 남음 (**장애 격리**)
- 정산 소비자를 추가해도 상환 처리 코드는 안 고침 (**결합도 분리**)

Kafka·RabbitMQ·SQS·Redis Stream은 전부 **"이 쪽지함을 어떻게 만들 것인가"에 대한 서로 다른 답**이다.

# 블록 1. "비동기 메시징 시스템을 사용해본 경험이 있나요?"

## 1-1. 이 질문의 정체

경험 유무를 묻는 질문이 아니라, **그 다음 5개 질문(유실·중복·순서·재처리·병목)의 입구**다.
여기서 어떻게 답하느냐가 남은 대화의 난이도를 결정한다.

## 1-2. 현재 위치 — 냉정하게

**브로커 운영 경험: 없음.** Kafka, RabbitMQ, SQS, Redis Stream 전부.

"조금 써봤다"는 위험하다. 아래 3개 중 하나만 물어도 드러난다.

- Consumer Group rebalance는 언제 일어나고 그동안 소비는 어떻게 되나
- offset commit 시점에 따라 at-least-once / at-most-once가 갈리는 지점
- 파티션 수를 바꾸면 무슨 일이 생기나

**그렇다고 "없습니다"로 끝내는 것도 오답.** 6년차 단답은 "생각해본 적 없다"로 읽힌다.

## 1-3. 실제로 가진 자산

브로커는 안 써봤지만 **브로커가 해결해주는 문제를 DB로 직접 풀어봤다.**

| 실무 | 대응하는 큐 개념 |
|---|---|
| 일괄 상환 `@Async` 비동기 처리 | 요청 경로에서 작업 분리 |
| 상태 컬럼 + 별도 트랜잭션 커밋 + 폴링 | **DB를 큐로 사용** |
| 성공/부분성공/실패 3분류, 실패 건만 재처리 | 부분 실패 · DLQ 문제의식 |
| 금결원 거래고유번호 = 멱등성 키 | **중복 소비 방어** |
| 연속 실패 시 자동 중지 | 연쇄 실패 차단 · circuit breaker |
| NH 대량이체 500건/회 | 처리량 확보(배치형) |

**멱등성 키가 결정적이다.** 큐의 핵심 난제가 중복 소비인데, 브로커 없이도 그 문제를 실무에서 만나 해결했다.
대부분의 지원자는 Kafka를 "썼다"고만 하고 **왜 멱등성이 필요한지는 못 말한다.**

## 1-4. 면접 답변 (그대로 말할 버전 · 약 50초)

> "Kafka나 RabbitMQ 같은 **메시지 브로커를 운영해 본 경험은 없습니다.** 다만 비동기 처리 자체는 실무에서 다뤘고, 큐가 겪는 문제는 같은 형태로 겪었습니다.
>
> P2P 금융 플랫폼에서 다건 일괄 상환을 처리할 때, 사용자 요청은 즉시 반환하고 실제 처리는 비동기로 분리했습니다. 처리 상태를 별도 트랜잭션으로 즉시 커밋해서 클라이언트가 폴링으로 진행률을 보게 했고, 결과는 성공·부분성공·실패로 나눠 실패 건만 재처리하도록 구성했습니다. **사실상 DB를 작업 큐처럼 쓴 구조**였습니다.
>
> 그래서 겪은 문제도 큐와 같았습니다. 재시도할 때 중복 이체가 나면 안 되니 **금융결제원 거래고유번호를 멱등성 키로** 써서 막았고, 연속 실패 시 자동 중지로 연쇄 실패를 끊었습니다.
>
> 다만 이 구조의 한계는 명확합니다. 폴링이라 지연이 있고, 작업이 **애플리케이션 프로세스 메모리 안에 있어서 인스턴스가 죽으면 유실**되며, 스케일아웃이 안 됩니다. 이 부분이 브로커가 필요해지는 지점이라고 이해하고 있습니다."

## 1-5. 이 답변이 강한 이유 4가지

1. **거짓이 없다** — 검증 표면적이 방어 가능한 범위로 좁혀진다. 면접관은 없다고 한 걸 파지 않는다
2. **문제를 겪은 증거가 구체적** — "부분 실패 분리", "멱등성 키"는 안 겪으면 안 나오는 단어
3. **한계를 스스로 말한다** — 면접관이 파려던 걸 먼저 꺼내면 **주도권이 넘어온다**
4. **자기 구조를 객관화** — "DB를 큐처럼 썼다"는 표현 자체가 추상화 능력의 증거

## 1-6. 마지막 한 줄 — 조건부 (10월 이후 사용 가능)

> "그래서 지금은 이 구조를 **Outbox 패턴과 Kafka로 다시 설계해 보는 프로젝트**를 진행 중입니다. 특히 DB 커밋과 메시지 발행 사이의 원자성 문제를 어떻게 푸는지가 핵심이라고 보고 있습니다."

- 지금(7월)은 사실이 아니므로 **쓰면 안 됨**
- `payment-settlement-core`가 굴러가는 10월 이후 유효 → 11월 지원 시점엔 사용 가능
- 붙으면 "경험 없음" → **"경험 없음 → 인지 → 실행 중"** 서사로 전환

## 1-7. 예상 꼬리질문

### ① "`@Async`랑 메시지 큐는 뭐가 다른가요?" ★ 거의 확실

> "가장 큰 차이는 **작업이 프로세스 안에 있느냐 밖에 있느냐**입니다. `@Async`는 애플리케이션 스레드풀에서 도는 거라 **서버가 내려가면 쌓여 있던 작업이 사라집니다.** 메시지 큐는 브로커에 영속되기 때문에 소비자가 죽어도 메시지가 남고, 살아나면 이어서 처리합니다.
>
> 두 번째는 확장입니다. `@Async`는 그 인스턴스 안에서만 병렬이지만, 큐는 소비자를 여러 인스턴스로 늘려 나눠 처리할 수 있습니다.
>
> 세 번째는 **배압(backpressure)** 입니다. `@Async`는 큐가 차면 작업이 거부되거나 호출 스레드가 막히는데, 브로커는 쌓인 양을 지표로 보면서 소비자를 늘리는 식으로 대응할 수 있습니다."

**3축 = 영속성 / 확장성 / 배압.**

### ② "DB를 큐로 쓴 게 왜 문제인가요?"

- **폴링 비용** — 처리할 게 없어도 주기적 조회. 주기를 줄이면 부하↑, 늘리면 지연↑
- **소비자 확장 어려움** — 여러 인스턴스가 같은 테이블 폴링 시 중복 획득. `SELECT ... FOR UPDATE SKIP LOCKED` 필요 → DB 경합
- **큐 부하가 서비스 DB에 그대로** — 큐가 밀리면 본 서비스 쿼리까지 느려짐

> 단, **소규모에선 DB 큐가 정답일 때가 많다**는 것도 같이 말할 것. "그 규모에선 합리적 선택이었다"는 판단이 들어가야 6년차.

### ③ "Kafka로 바꾸면 뭐가 좋아지나요?"

"빠릅니다"는 감점. 처리량은 결과지 이유가 아니다.
축 3개 — **영속성 있는 버퍼 / 소비자 독립 확장 / 발행자-소비자 분리(fan-out)**.

### ④ "폴링 주기는 얼마로 잡았나요?"

⚠️ **실제 값 확인 필요 (본업 코드).** 못 답하면 "직접 설계했다"가 통째로 흔들린다.
값 + **왜 그 값인지**(체감 지연 vs DB 부하 균형)를 같이 말해야 함.

### ⑤ "브로커 경험이 없는데 입사하면 바로 할 수 있나요?"

> "운영 경험이 없다는 건 인정합니다. 다만 큐가 푸는 문제 — 멱등성, 부분 실패, 재처리 — 는 실무에서 다뤄봤기 때문에 도구를 익히는 구간만 남았다고 봅니다."

## 1-8. 블록 1 결론

> **"브로커는 안 써봤다. 그러나 브로커가 푸는 문제는 DB로 직접 풀어봤고, 그 구조의 한계도 안다."**

# 블록 2. "왜 메시지 큐를 도입했나요?"

이유만 말하면 반쪽. **대가까지 말해야 완성**된다.

## 2-1. 면접 답변

> "도입 목적은 크게 세 가지로 봅니다. 사용자 **응답 시간을 떼어내는 것**, 외부 시스템 장애를 **격리하는 것**, 트래픽 피크를 **버퍼로 흡수하는 것**입니다. 어느 쪽이 목적이냐에 따라 설계가 달라집니다.
>
> 응답 시간이 목적이면 결과적 일관성을 감수해야 하고, 장애 격리가 목적이면 재처리와 DLQ 설계가 핵심이 됩니다. 그래서 '큐를 쓸까'보다 **'무엇을 사용자 요청 경로에서 빼낼 수 있는가'** 를 먼저 봅니다."

## 2-2. 도입 이유 4가지 — 각각 설계가 달라진다

| 목적 | 상황 | 이때 중요해지는 것 |
|---|---|---|
| **① 응답 시간 분리** | 주문 후 알림·집계·정산 예약 | 결과적 일관성 수용, 상태 노출 |
| **② 장애 격리** | 외부 PG·은행이 죽어도 주문은 받아야 함 | 재시도 정책, DLQ, 백오프 |
| **③ 트래픽 버퍼링** | 이벤트·마감일 피크 흡수 | 적체 모니터링, 소비자 스케일아웃 |
| **④ 결합도 분리 (fan-out)** | 결제 1건 → 정산·알림·데이터팀 3곳 소비 | 토픽 설계, 소비자별 독립 진행 |

④가 실무에서 제일 크게 작동하는데 이력서엔 잘 안 쓰인다.
**"소비자를 추가할 때 발행자 코드를 안 고쳐도 되는 구조"** — 이벤트 기반 구조의 본질.

## 2-3. 내 실무 매핑

- 일괄 상환 `@Async` → **①**
- NH 대량이체 배치(500건/회) → **③** 성격.
  ⚠️ **배치와 큐의 차이를 말할 수 있어야 한다.** 배치는 "정해진 시각에 몰아서"(지연이 주기에 묶임), 큐는 "들어오는 대로 흘려서"(지연이 소비 속도에 묶임)
- 실패 건만 재처리 → **②**의 문제의식

## 2-4. 반드시 같이 말할 것 — 대가

장점만 말하면 "그럼 다 큐로 하면 되겠네요?"로 되받힌다.

| 대가 | 내용 |
|---|---|
| **결과적 일관성** | 즉시 정합이 필요한 건 못 뺀다. 잔액 차감을 비동기로 빼면 이중 사용 발생 |
| **순서 보장 비용** | 전역 순서는 사실상 포기. 키 단위(파티션) 순서로 타협 |
| **중복 발생 전제** | 대부분 at-least-once → **소비자 멱등성이 필수 요구사항** |
| **운영 복잡도** | 브로커 자체가 장애 지점. 적체·lag 모니터링, DLQ 운영 |
| **디버깅 난이도** | 호출 스택이 끊긴다. **Trace ID 전파 없으면 원인 추적 불가** |

## 2-5. 판단 기준 (외울 것)

> **"실패해도 사용자에게 즉시 알릴 필요가 없고, 늦게 처리돼도 되는 것"만 큐 뒤로 보낸다.**
> 즉시 정합이 필요한 건 트랜잭션 안에 남긴다.

# 블록 3. 4대 시스템 비교

## 3-0. 먼저 — 이것들의 물리적 정체

**Kafka·RabbitMQ·Redis는 전부 "따로 돌아가는 서버 프로그램"이다. MySQL과 같은 위치.**

```
MySQL     = 데이터를 저장해주는 별도 서버 프로세스
Kafka     = 메시지를 저장·전달해주는 별도 서버 프로세스
RabbitMQ  = 메시지를 배달해주는 별도 서버 프로세스
```

**Java 라이브러리가 아니다.** `import` 하는 게 아니라 **다른 프로세스로 따로 켜져 있는 프로그램**이다.

| | 만들어진 언어 | 실행 |
|---|---|---|
| Kafka | **Java/Scala** | JVM 프로세스 (→ 그 서버에 JDK 필요, GC 튜닝 이슈 존재) |
| RabbitMQ | Erlang | Erlang VM 프로세스 |
| Redis | C | 네이티브 프로세스 |
| SQS | 비공개 | **설치 개념 없음. AWS가 운영** |

**만들어진 언어는 나와 무관하다.** MySQL이 C인데 C를 몰라도 되는 것과 같다.
나는 Java 클라이언트 라이브러리로 접속만 한다.

**3층 구조**

```
① 브로커 (서버 프로세스)     Kafka / RabbitMQ / Redis   ← Docker·AWS로 띄움. 인프라
② 클라이언트 라이브러리       spring-kafka / spring-amqp  ← build.gradle에 추가
③ 애플리케이션 코드           @KafkaListener, send()      ← 내가 짜는 부분

* MySQL로 치환: ① mysqld  ② mysql-connector-j  ③ MyBatis Mapper — 완전히 같은 그림
```

**코드에서 보이는 모습**

```yaml
# 지금 쓰는 것
spring.datasource.url: jdbc:mysql://localhost:3306/mydb
# Kafka 추가하면 (주소:포트 알려주는 것 — 완전히 같은 패턴)
spring.kafka.bootstrap-servers: localhost:9092
```

// 발행 — 네트워크로 Kafka 서버에 메시지 전송
kafkaTemplate.send("repayment-completed", 채권ID.toString(), json);

// 소비 — Kafka가 메시지를 주면 이 메서드가 자동 호출됨

## 3-1. 두 계열로 갈린다 ★ 가장 중요한 구분

| 계열 | 비유 | 소비 방식 | 해당 |
|---|---|---|---|
| **큐(Queue) 계열** | 은행 대기표 | 꺼내면 **사라짐** | RabbitMQ, SQS |
| **로그(Log) 계열** | 녹화 방송 | 읽어도 **남아있음**, 각자 offset 기억 | Kafka, Redis Stream |

```
[큐 계열]  📮 [3번][4번][5번] → 직원이 3번 뽑아감 → 3번은 사라짐

[로그 계열] 📼 1화 2화 3화 4화 5화 6화   ← 봐도 안 사라짐
                    ↑         ↑
               영희(3)      철수(6)     ← 각자 위치를 따로 기억
```

## 3-2. 공통 상황으로 비교

**월요일 10시, 일괄 상환 1,800건 처리. 상환 1건마다 "상환 완료" 이벤트 발생.**

```
                          ┌─→ ① 알림톡 발송
[상환 완료] 이벤트 1,800건 ─┼─→ ② 정산 집계
                          └─→ ③ 데이터 적재
```

**⚠️ 이 셋은 순차가 아니라 완전 독립·동시다.** 애초에 별개 프로세스라 서로를 참조할 방법이 없다.
알림톡이 #57 처리 중일 때 정산은 #300일 수 있다.

```
순서에는 두 층이 있다
  가로(소비자들 사이) : 순서 없음. 완전 독립
  세로(한 소비자 안)  : 순서 있음. 같은 파티션 내 발생 순서대로
```

진짜 순차가 필요하면 → **이벤트 체이닝**(정산 완료 후 "정산 완료" 이벤트 발행 → 알림톡이 구독) 또는 **애초에 큐로 안 뺌**(트랜잭션에 남김).

**사고 발생 — 오후 3시**

> 알림톡 코드 버그로 1,800건이 전부 금액 0원으로 발송됨. 코드는 고쳤다. 다시 보내야 한다.

### 🟦 Kafka

```
토픽: repayment-completed  (보관 7일)
[1][2][3] ......... [1798][1799][1800]
     ↑알림톡           ↑정산            ↑데이터
```

**사고 대응**
```bash
kafka-consumer-groups --reset-offsets --to-datetime 2026-07-27T10:00:00 \
  --group notification-group --topic repayment-completed
```
→ 알림톡 소비자만 되감아 1,800건 재발송. **정산·데이터는 무영향.**

**얻는 것**
- 이벤트가 7일 남아 있어 **"그때로 돌아가기"가 명령 한 줄**
- 나중에 "④ 세무 데이터"가 필요하면 **새 소비자를 붙여 과거 7일치를 처음부터** 읽으면 됨. 발행 코드 수정 0

**핵심 개념**

| 용어 | 뜻 |
|---|---|
| Topic | 메시지 분류 단위 |
| **Partition** | 토픽을 쪼갠 물리 단위. **병렬 처리 최소 단위이자 순서 보장 범위** |
| Offset | 파티션 내 위치. 소비자가 관리 |
| Consumer Group | 같은 그룹=파티션 나눠 먹음 / 다른 그룹=같은 메시지 각자 다 받음 |

⚠️ **파티션을 나누면 전체 순서는 깨진다.** 그래서 **파티션 키**를 쓴다.
→ 내 도메인: **같은 채권의 상환 이벤트가 뒤바뀌면 잔액이 틀어진다 → 채권번호를 파티션 키로.**

**대가**: 브로커 클러스터를 짓고 운영. 하루 1,800건에는 과잉. **하루 수백만 건일 때 값을 한다.**

### 🟩 RabbitMQ

```
                    ┌→ 📮 알림톡 큐 → 소비자 → 처리 후 삭제
[상환 완료] → Exchange ┼→ 📮 정산 큐   → 소비자 → 처리 후 삭제
                    └→ 📮 데이터 큐 → 소비자 → 처리 후 삭제
```

**사고 대응**: 큐가 비어있음. **되돌릴 방법 없음.** DB에서 1,800건 재조회 → 재발송 스크립트 작성 → 반나절.

**대신 압도적인 것 — 라우팅**

> "상환 금액 1,000만원 이상은 담당자 확인, 미만은 일반 알림톡"

```
                    ┌─[repayment.vip]───→ 📮 VIP 큐
[상환 완료] → Exchange ┤
                    └─[repayment.normal]→ 📮 일반 큐
```

**Kafka는** 소비자가 1,000건 다 읽고 999건을 코드에서 버린다.
**RabbitMQ는** VIP 소비자에게 **애초에 1건만 도착**한다. if문이 코드에 없다.

| Exchange 타입 | 판단 기준 |
|---|---|
| direct | 라우팅 키 정확히 일치 |
| topic | 패턴 매칭 (`repayment.*.failed`) |
| headers | 헤더 값 |
| fanout | 조건 없이 전부 복사 |

⚠️ **오해 주의**: SQL WHERE 절이 아니다. **값 비교(`amount > 1000만`)는 못 한다.**
브로커가 보는 건 **발행 시 붙인 라우팅 키 문자열**이고, 판단 자체는 발행 쪽에서 한다.

```java
String key = (amount >= 10_000_000) ? "repayment.vip" : "repayment.normal";
rabbitTemplate.convertAndSend("repayment-exchange", key, event);
```

**그럼 뭐가 이득인가** → 발행자는 **"분류"만** 하고 어느 큐로 가는지·소비자가 몇 개인지 모른다.
"VIP 건은 감사 로그도 남기자" → **큐 하나 추가 바인딩. 발행자 코드 수정 0.**

> 한 줄: 조건절을 대신 써주는 게 아니라 **"분류"와 "배달 경로"를 분리**해주는 것.

### 🟨 SQS

```
[상환 완료] → 📮 SQS → 소비자
              (Visibility Timeout 안에 삭제 안 하면 다시 나옴)
```

**실제로 벌어지는 중복**
```
10:00:00  이벤트 #57 꺼냄        → 30초간 다른 소비자에게 안 보임
10:00:12  알림톡 발송 성공 ✅
10:00:13  "삭제" 호출 직전 서버 다운 💥
10:00:30  #57 다시 나타남
10:00:35  다른 소비자가 또 발송 ❌
```

**SQS 기본은 at-least-once — "두 번 갈 수 있다"가 전제다.**

```java
if (처리이력.존재(이벤트ID)) return;   // ← 멱등성. 필수
알림톡_발송();
처리이력.기록(이벤트ID);
```

> 💡 **이게 내가 이미 해본 것.** 금결원 거래고유번호를 멱등성 키로 써서 중복 이체를 막은 구조와 **완전히 같은 패턴.** 면접에서 이 연결을 말하면 강하다.

| | Standard | FIFO |
|---|---|---|
| 순서 | ❌ | ✅ 그룹 내 |
| 중복 | at-least-once | 중복 제거 지원 |
| 처리량 | 사실상 무제한 | 제한 있음 |

**압도적인 것**: 서버 없음, 콘솔 클릭 3번, 자동 확장, 요청당 과금. **인프라 담당 없는 팀엔 결정적.**

### 🟥 Redis Stream

**전제**: 이미 Redis를 세션·캐시로 쓰고 있는 회사.

Kafka 축소판. 이벤트가 남고, 그룹별 진도를 따로 관리한다.

**사고 대응**
```
XGROUP SETID repayment-completed notification-group 0
```
→ Kafka와 동일하게 재처리 가능.

**Stream만의 장치 — PEL (Pending Entries List)**

```
📋 읽었지만 아직 ack 안 된 목록
  ├ #57 · 소비자A · 180초 경과   ← A가 죽은 듯
  └ #58 · 소비자B · 2초 경과
→ 소비자C: XAUTOCLAIM으로 #57 뺏어옴
```

| 명령 | 역할 |
|---|---|
| `XADD` | 발행 |
| `XREADGROUP` | 그룹으로 소비 |
| `XACK` | 처리 완료 → PEL에서 제거 |
| `XPENDING` | 밀린 것 조회 (**장애 진단이 눈에 보임**) |
| `XCLAIM` / `XAUTOCLAIM` | 죽은 소비자 것 가져오기 |

SQS는 시간이 지나야 자동 재노출되지만, Stream은 **누가 뭘 물고 있는지 목록으로 보인다.**

**약점**: 기본이 **메모리**. Redis가 죽으면 최근 이벤트 유실 가능. 장기 보관은 메모리 비용.
→ **판단 기준**: 알림톡 몇 건 날아가는 건 감수 가능 → Stream. **이체 이벤트가 날아가면 돈이 안 맞음 → Kafka.**

## 3-4. 한 장 요약

| | Kafka | RabbitMQ | SQS | Redis Stream |
|---|---|---|---|---|
| 성격 | 이벤트 로그 | 메시지 브로커 | 관리형 큐 | 경량 로그 |
| 소비 후 | 남음 (replay ✅) | 삭제 | 삭제 | 남음 (replay ✅) |
| 순서 | 파티션 내 | 큐 내 | FIFO만 | 스트림 내 |
| 라우팅 | 단순(토픽) | **매우 강함** | 단순 | 단순 |
| 운영 부담 | 높음 | 중간 | **없음** | 낮음 |
| 처리량 | 최상 | 중 | 높음 | 높음(메모리 한계) |
| 내구성 | 최상 | 높음 | 높음 | **중** |

**상황별 선택**

| 이 회사라면 | 선택 | 이유 |
|---|---|---|
| 하루 1,800건, 인프라 담당 없음, AWS | **SQS** | 운영 0. Kafka는 과잉 |
| 하루 1,800건, 이미 Redis 사용, 재처리 필요 | **Redis Stream** | 인프라 추가 없이 replay 확보 |
| 금액대별·상태별 분기가 계속 늘어남 | **RabbitMQ** | 라우팅을 브로커가 |
| 수백만 건, 여러 팀 소비, 감사·재처리 필수 | **Kafka** | 조건이 다 모이면 대안 없음 |

> **최우선 판단**: **"이벤트를 나중에 다시 볼 일이 있는가?"**
> 있다 → Kafka / Redis Stream · 없다 → RabbitMQ / SQS
> **금융은 거의 항상 "있다"** (감사·대사·정합성 검증)

# 블록 3-부록. ack — "완료를 안 보내면 어떻게 되나"

면접 단골. 경우를 나눠서 봐야 한다.

**대전제**
```
소비자가 메시지 꺼냄 → 큐에서 삭제되는 게 아니라 "처리중(unacked)" 상태
                    → ack  → 그때 진짜 삭제
                    → nack → 재전달 or DLQ
```
**ack 전까지 메시지는 브로커가 계속 들고 있다.**

### ① 소비자가 죽었다
RabbitMQ는 **TCP 연결 끊김을 감지** → 즉시 큐로 되돌림(requeue) → 다른 소비자에게 재전달. **유실 없음.**

> SQS와의 차이: SQS는 연결 개념이 없어 **Visibility Timeout(시간)이 지나야** 재노출. RabbitMQ는 **즉시** 감지.

### ② 살아있는데 ack를 안 보낸다 ★ 진짜 위험
연결이 살아있으니 죽었다고 판단 안 함 → **무한정 기다린다.**
(3.8.15+ `consumer_timeout` 기본 30분, 초과 시 채널 강제 종료)

**prefetch와 결합하면 서비스가 멈춘다**
```
prefetch = 10 (unacked 10개면 더 안 줌)
소비자A가 10개 받고 전부 ack 안 함
→ 브로커: "A는 배부르네" → 더 안 줌
→ 소비자가 A뿐 → 큐에 1,790건 쌓이는데 아무도 처리 못 함  💥 완전 정지
```
**진단**: 관리 콘솔에서 `Ready`(대기) vs `Unacked`(처리중). **Unacked가 안 줄면 이 상황.**

> 💡 커넥션 풀 **누수(leak) 패턴과 완전히 동일**. 빌렸는데 안 돌려주는 것. 진단법도 같다 — **트래픽이 빠져도 안 줄면 소비자 문제.**

### ③ nack — requeue 값이 갈림길

| requeue | 결과 | 위험 |
|---|---|---|
| true | 큐로 되돌림 | **무한 루프.** 데이터 자체가 잘못이면 영원히 재시도 |
| false | 버림 / DLQ로 이동 | 안전 |

**정석**: 1차 실패 → 재시도 / 2~3차 실패 → **DLQ 격리** / DLQ는 사람이 본다(알림).
DLQ 없으면 실패 메시지가 큐를 돌며 정상 처리까지 방해한다.

### ④ auto-ack — 가장 흔한 버그
```
10:00:00  메시지 받는 즉시 ack → 브로커에서 삭제
10:00:02  처리 중 서버 다운 💥
→ 영구 유실. 브로커에 흔적도 없음
```
**금융에서 auto-ack는 금지.** 반드시 수동 ack로 **처리 완료 후** 전송.
Spring AMQP: `acknowledge-mode: manual` (참고: 기본값 `AUTO`는 auto-ack가 아니라 "예외 없이 끝나면 ack, 예외 나면 nack". 이름 혼동 주의)

### ⑤ ack 타이밍이 결정하는 배달 보장

| ack 시점 | 보장 | 결과 |
|---|---|---|
| 처리 **전** (auto-ack) | at-most-once | 유실 가능, 중복 없음 |
| 처리 **후** (manual) | **at-least-once** | 유실 없음, **중복 가능** |

**처리 후 ack를 해도 중복은 남는다** — 처리 완료 후 ack 직전 다운 → 재전달 → 재처리.

> **그래서 결론은 항상 같은 곳으로 간다 — 소비자는 멱등해야 한다.**
> RabbitMQ든 SQS든 Kafka든, at-least-once를 택하는 순간 중복은 막을 수 없고,
> **중복이 와도 결과가 같게 만드는 것**이 유일한 답이다.

### 면접 답변 압축

> "ack는 소비자가 처리를 끝냈다고 브로커에 알리는 신호이고, ack 전까지 메시지는 브로커에 남아 있습니다. 소비자가 죽으면 연결 끊김을 감지해 다른 소비자에게 재전달합니다.
>
> 주의할 건 두 가지입니다. **auto-ack는 처리 전에 ack가 나가 유실 위험**이 있으므로 유실이 곤란한 곳에서는 수동 ack로 처리 후에 보내야 합니다. 둘째, 처리 후 ack를 해도 **ack 직전에 죽으면 중복**이 발생하므로 at-least-once를 전제로 **소비자를 멱등하게 설계**해야 합니다.
>
> 그리고 실패 시 requeue만 하면 무한 루프가 되므로, 재시도 횟수를 제한하고 초과분은 DLQ로 격리하는 구성이 필요합니다."

# 블록 4. Redis 3형제 — List / Pub-Sub / Stream

원 질문의 두 번째 문장이 여기다. **"메시지 큐를 Redis로 구현하거나 최적화한다면 무엇을 먼저 고려해야 할까요?"**

Redis로 큐를 만드는 방법은 3가지고, **셋의 성질이 완전히 다르다.** 어느 걸 고르느냐가 곧 유실·중복 설계다.

## 4-1. 같은 상황을 3가지로 구현해보기

**상황**: 상환 완료 → 알림톡 발송

### 🅐 List — 가장 원시적인 큐

```
발행자:  LPUSH notify-queue "{상환ID:57}"      ← 왼쪽에 밀어넣음
큐 상태: [57][56][55][54]
소비자:  BRPOP notify-queue 0                  ← 오른쪽에서 꺼냄. 큐에서 사라짐
```

**`BRPOP`의 B = Blocking.** 큐가 비어있으면 **메시지가 올 때까지 대기**한다. 폴링이 아니라 대기.
→ **DB 폴링 대비 결정적 이점.** CPU도 안 쓰고 지연도 없다.

**구현 난이도 최저.** 명령 2개면 큐가 된다.

**치명적 약점**
```
10:00:00  소비자A: BRPOP으로 #54 꺼냄 → 큐에서 즉시 삭제
10:00:01  알림톡 발송 중...
10:00:02  소비자A 💥 다운
→ #54는 어디에도 없다. 영구 유실.
```

**꺼내는 순간 사라진다. ack가 없다.** → **auto-ack와 같은 문제. at-most-once.**

**보완책 — `BRPOPLPUSH` (또는 `BLMOVE`)**
```
BRPOPLPUSH notify-queue processing-queue 0   ← 꺼내면서 "처리중 큐"로 옮김 (원자적)
처리 완료 → LREM processing-queue 1 "{...}"
소비자 죽음 → processing-queue에 남음 → 별도 감시 프로세스가 되돌림
```
**ack를 손으로 구현하는 것**이고 `processing-queue`가 **PEL의 수동 버전**이다.
→ 여기까지 오면 "그냥 Stream 쓰지" 가 된다.

### 🅑 Pub/Sub — 큐가 아니다

**이건 큐가 아니라 방송이다.** 이름 때문에 착각하기 쉽다.

```
발행자:  PUBLISH notify-channel "{상환ID:57}"
         구독자A ← 받음 (지금 접속 중)
         구독자B ← 받음
         구독자C   ✗  (지금 접속 안 함 → 영원히 못 받음)
```

| 특성 | 내용 |
|---|---|
| 저장 | **안 함.** 발행 즉시 현재 구독자에게 뿌리고 끝 |
| 구독자 없으면 | **메시지 소멸.** 흔적도 없음 |
| ack | 없음 |
| 소비자 죽으면 | 그동안 온 메시지 전부 유실 |
| 여러 구독자 | **전부 같은 메시지를 받음** (나눠 먹기 아님) |

**"TV 생방송"이다.** 지금 틀고 있는 사람만 본다. 녹화 없음.

> ⚠️ RabbitMQ는 소비자 여러 개면 **나눠 먹는다**(로드밸런싱).
> Pub/Sub은 소비자 여러 개면 **전부 똑같이 받는다**(브로드캐스트).
> → 알림톡 소비자를 2개 띄우면 **알림이 2번 간다. 스케일아웃 불가.**

**어디에 쓰나 — 용도가 따로 있다**

| 용도 | 왜 맞나 |
|---|---|
| **캐시 무효화 신호** | "상품 123 캐시 지워" → 전 서버가 받아야 함. 놓쳐도 다음 조회 때 갱신 |
| **실시간 알림 푸시** | 채팅, 대시보드. 놓친 메시지는 어차피 의미 없음 |
| **서버 간 설정 동기화** | "설정 리로드해" |

**공통점: 유실돼도 되는 것 + 전원이 받아야 하는 것.**

> 💡 **결제·정산에는 절대 금지.** 이체 이벤트를 Pub/Sub으로 보내면 소비자 재시작 중에 온 건 그냥 사라진다.

### 🅒 Stream — 제대로 된 큐

Kafka 축소판. **List의 유실 문제와 Pub/Sub의 확장 문제를 둘 다 해결.**

```
발행:  XADD repayment-stream * repaymentId 57 amount 1000000
                             ↑ ID 자동 생성(타임스탬프-시퀀스)

스트림: [1-0][2-0][3-0]...[1800-0]     ← 읽어도 안 사라짐

소비:  XREADGROUP GROUP notify-group consumer-1 COUNT 10 BLOCK 0 STREAMS repayment-stream >
       → 아직 아무도 안 읽은 것 10건 + PEL 등록

완료:  XACK repayment-stream notify-group 1-0    → PEL에서 제거
```

**핵심 장치 — PEL (Pending Entries List)**
```
📋 읽었지만 아직 ack 안 된 목록
  ├ 1-0 · consumer-1 · 180초 경과   ← 죽은 듯
  └ 2-0 · consumer-2 · 2초 경과

XPENDING repayment-stream notify-group     ← 밀린 것 조회
XAUTOCLAIM ... MIN-IDLE-TIME 60000         ← 60초 넘게 물고 있는 것 뺏어오기
```

**Consumer Group 두 가지 모드**
```
같은 그룹 안 소비자들  → 나눠 먹음 (스케일아웃 ✅)
서로 다른 그룹         → 같은 메시지를 각자 다 받음 (fan-out ✅)

notify-group    : consumer-1, consumer-2   ← 1,800건을 900씩
settlement-group: consumer-1               ← 1,800건 전부
```

**Kafka와 완전히 같은 모델.** Stream을 익히면 Kafka 개념이 거의 그대로 넘어간다.

## 4-2. 3형제 비교표

| | **List** | **Pub/Sub** | **Stream** |
|---|---|---|---|
| 명령 | `LPUSH`/`BRPOP` | `PUBLISH`/`SUBSCRIBE` | `XADD`/`XREADGROUP` |
| 메시지 보존 | 꺼내면 삭제 | **저장 안 함** | **남음** (replay ✅) |
| 소비자 없을 때 | 큐에 쌓임 | **소멸** | 쌓임 |
| ack | ❌ | ❌ | ✅ `XACK` |
| 소비자 죽으면 | **유실** | 유실 | **PEL에 남음 → 재할당** |
| 소비자 여러 개 | 나눠 먹기 | **전부 같은 걸 받음** | 그룹 내 나눠 먹기 |
| Consumer Group | ❌ | ❌ | ✅ |
| 배달 보장 | at-most-once | 보장 없음 | **at-least-once** |
| 구현 난이도 | 최저 | 최저 | 중 |
| Redis 버전 | 1.0 | 2.0 | **5.0+** |

## 4-3. 선택 기준

```
유실돼도 되나?
├ 예 → 전원이 받아야 하나?
│      ├ 예   → Pub/Sub  (캐시 무효화, 실시간 알림)
│      └ 아니오 → List    (가벼운 작업 큐)
└ 아니오 → Stream  ★ 금융은 거의 항상 여기
```

> **결제·정산·이체 = 무조건 Stream.** List나 Pub/Sub은 검토 대상도 아니다.

## 4-4. ★ 원 질문에 대한 답 — "Redis로 큐를 만든다면 무엇을 먼저 고려하나"

자료구조 나열이 아니라 **고려 순서**를 말해야 한다.

### 면접 답변

> "가장 먼저 보는 건 **메시지 유실을 허용할 수 있는가**입니다. 이 답에 따라 자료구조가 갈립니다.
>
> List는 `BRPOP`으로 꺼내는 순간 사라지고 ack가 없어서, 소비자가 처리 중에 죽으면 유실됩니다. Pub/Sub은 아예 저장하지 않아서 구독자가 없는 순간 소멸합니다. 결제나 이체처럼 유실이 허용되지 않는 도메인에서는 둘 다 쓸 수 없다고 봅니다.
>
> 그래서 **Stream을 기본 선택지로 두고**, Consumer Group과 PEL로 ack와 재할당을 확보합니다. 다만 Stream은 at-least-once라 중복이 발생하므로 **소비자 멱등성 설계가 세트로** 따라와야 합니다.
>
> 그다음은 **메모리 관리**입니다. Redis는 기본이 메모리라 스트림이 무한히 자라면 위험하므로 `XTRIM`이나 `MAXLEN` 정책이 필요하고, 이 보관 기간이 곧 재처리 가능 범위가 됩니다.
>
> 마지막은 **내구성 한계를 명확히 인지하는 것**입니다. Redis는 AOF나 복제를 켜도 Kafka 수준의 내구성은 나오지 않습니다. 그래서 **돈이 직접 걸린 이벤트라면 Redis 큐만 믿지 않고, DB 상태를 원본으로 두고 큐는 트리거로만 쓰거나 대사 배치로 보정하는 구조를 함께 둡니다.**"

**마지막 문단이 급을 결정한다.** "만들 수 있어요"가 아니라 **"어디까지 믿고 어디부터 안 믿는가"**.

### 고려 순서 5단계 (외울 것)

| 순서 | 질문 | 결론 |
|---|---|---|
| ① | **유실 허용되나?** | 아니오 → Stream 확정 |
| ② | **중복 방어는?** | at-least-once 전제 → **멱등성 키 필수** |
| ③ | **메모리 한계는?** | `MAXLEN`/`XTRIM` → 보관량 = 재처리 범위 |
| ④ | **소비자 장애 시?** | PEL + `XAUTOCLAIM` + 재시도 상한 + DLQ 스트림 |
| ⑤ | **내구성 한계는?** | Redis는 Kafka만 못함 → **DB를 원본으로, 대사로 보정** |

## 4-5. 실무 설계 — 내 도메인에 적용

```
[상환 처리]
   ├─ ① DB에 상환 내역 저장 (원본. 여기가 진실)
   └─ ② XADD로 이벤트 발행
              ↓
      [Redis Stream: repayment-events]
   ┌──────────┴──────────┐
[notify-group]      [settlement-group]
 알림톡 소비자          정산 소비자
   ├ 멱등성 체크(상환ID)  ├ 멱등성 체크
   ├ 처리                ├ 처리
   └ XACK               └ XACK

   [야간 대사 배치]  DB 상환 내역 vs 실제 발송/정산 결과 → 누락분 보정
```

1. **DB가 원본, Stream은 트리거.** Stream이 날아가도 DB에서 복구 가능
2. **소비자마다 멱등성 체크** — 중복 소비 전제
3. **대사 배치가 최종 안전망** — 비동기는 반드시 틀어진다는 전제

> ⚠️ **여기서 다음 주제가 나온다 — Outbox 패턴**
> ①과 ②가 원자적이지 않다. DB 커밋 후 `XADD` 직전에 죽으면 **DB엔 있는데 이벤트는 없다.**
> → 블록 5-1 참조. `payment-settlement-core`의 핵심 항목.

## 4-6. 예상 꼬리질문

**Q. "Pub/Sub도 메시지 큐 아닌가요?"**
> "이름은 그렇지만 저장하지 않기 때문에 큐로 보기 어렵습니다. 구독자가 없으면 소멸하고, 소비자를 여러 개 띄우면 나눠 먹는 게 아니라 전부 같은 메시지를 받습니다. 캐시 무효화 신호처럼 유실돼도 되고 전원이 받아야 하는 용도에 맞습니다."

**Q. "List로도 ack를 구현할 수 있지 않나요?"**
> "`BRPOPLPUSH`로 처리중 큐에 옮겨두고 완료 시 제거하는 방식으로 흉내낼 수 있습니다. 다만 처리중 큐를 감시해 되돌리는 로직을 직접 짜야 하는데, 그건 Stream의 PEL을 수동 구현하는 것이라 Stream을 쓰는 게 합리적이라고 봅니다."

**Q. "Redis Stream 대신 Kafka를 써야 하는 시점은?"**
> "세 가지로 봅니다. 유실이 절대 허용되지 않을 때(Redis는 복제 지연 중 장애에서 유실 가능), 보관 기간이 길어야 할 때(Redis는 메모리 비용, Kafka는 디스크), 처리량이 Redis 단일 인스턴스 한계를 넘을 때입니다."

**Q. "Stream이 계속 쌓이면요?"**
> "`XADD ... MAXLEN ~ 100000`으로 상한을 두거나 `XTRIM`으로 주기적으로 잘라냅니다. 다만 이 보관량이 곧 재처리 가능 범위이므로 대사 주기보다는 길게 잡아야 합니다."

# 블록 5. 유실 · 중복 · 순서 · 재처리 · 처리량

원 질문의 꼬리질문 전부가 여기 모인다. 이 5개는 따로 있는 문제가 아니라 **하나의 트레이드오프 축 위에 있다.**

## 5-0. 모든 것을 관통하는 하나 — 배달 보장

```
at-most-once   :  유실 O · 중복 X   (처리 전에 ack)
at-least-once  :  유실 X · 중복 O   (처리 후에 ack)   ← 실무 표준
exactly-once   :  유실 X · 중복 X   (사실상 신화)
```

**유실과 중복은 동시에 없앨 수 없다.** 둘 중 하나를 고르는 문제다.

> **업계 표준 답: at-least-once를 택하고, 중복은 소비자 멱등성으로 흡수한다.**
> 유실은 복구 불가능하지만 중복은 설계로 막을 수 있기 때문.

> ⚠️ **"Kafka는 exactly-once 되지 않나요?"**
> Kafka의 EOS는 **Kafka 내부에서만** 성립한다(트랜잭셔널 프로듀서 + 읽기-처리-쓰기가 전부 Kafka 안일 때).
> **소비자가 외부 DB나 외부 API를 건드리는 순간 깨진다.** 이체 API를 호출하면 Kafka는 그 결과를 모른다.
> → **금융에서 exactly-once를 믿으면 안 된다.** 이 문장을 말할 수 있으면 상당히 위.

## 5-1. 유실 (Message Loss)

유실은 **3군데**에서 발생한다. 한 군데만 막으면 소용없다.

```
[발행자] ──①──▶ [브로커] ──②──▶ [소비자]
                    ③ (브로커 자체)
```

### ① 발행 구간 — 가장 많이 놓치는 곳

```java
kafkaTemplate.send("repayment", event);   // 비동기. 결과를 안 봄
// → 브로커가 죽어 있어도 코드는 그냥 지나간다
```

| 대책 | 내용 |
|---|---|
| **acks 설정** | `acks=all` — 리더+팔로워 복제까지 확인 (`acks=0` 확인 안 함, `acks=1` 리더만) |
| **발행 결과 확인** | 콜백 또는 `.get()`으로 실패 감지 → 재시도 |
| **★ Outbox 패턴** | 아래 |

### ★ Outbox 패턴 — 발행 유실의 근본 해법

```java
@Transactional
public void 상환처리() {
    repaymentMapper.insert(...);     // DB 커밋
    kafkaTemplate.send(...);          // ← 여기서 죽으면?
}
```
**DB엔 상환이 기록됐는데 이벤트는 안 나갔다.** 알림도 정산도 영원히 안 온다.
순서를 바꾸면? 이벤트는 나갔는데 DB 커밋 실패 → **없는 상환에 대한 알림.**

> **DB와 브로커는 별개 프로세스다.** 하나의 트랜잭션으로 못 묶는다. (2PC는 실무에서 거의 안 씀)

**해법: 이벤트도 DB에 같이 저장한다**
```java
@Transactional
public void 상환처리() {
    repaymentMapper.insert(...);        // ① 업무 데이터
    outboxMapper.insert(event);         // ② 이벤트를 outbox 테이블에
}   // ← 같은 트랜잭션. 원자적으로 성공/실패

// 별도 프로세스: outbox를 읽어 브로커로 발행 → 성공 시 published 표시
```
```
outbox 테이블
┌────┬──────────────┬─────────┬───────────┐
│ id │ aggregate_id │ payload │ published │
├────┼──────────────┼─────────┼───────────┤
│ 1  │ 상환-57      │ {...}   │ true      │
│ 2  │ 상환-58      │ {...}   │ false ←미발행 │
└────┴──────────────┴─────────┴───────────┘
```
**얻는 것**: 발행 프로세스가 죽어도 outbox에 남아 **재시작하면 이어서 발행.** 유실 0.
**대가**: 발행 지연(폴링 주기), outbox 관리, **중복 발행 가능**(발행 후 표시 전 다운) → 다시 멱등성으로.

> 💡 **`payment-settlement-core`의 핵심 항목.** 그리고 **내 실무와 연결된다** —
> 상태 컬럼을 별도 트랜잭션으로 커밋하고 폴링한 구조가 **Outbox의 원시적 형태**다.

### ② 브로커 구간

| 대책 | 내용 |
|---|---|
| 복제 | Kafka `replication.factor=3` — 브로커 1대 죽어도 유지 |
| `min.insync.replicas` | 최소 몇 대에 써야 성공으로 볼지 (보통 2) |
| 디스크 flush | 메모리에만 있으면 정전 시 유실 |

> ⚠️ **Redis Stream의 약점.** AOF·복제를 켜도 **복제가 비동기**라 마스터가 죽는 순간 최근 몇 건이 유실될 수 있다. Kafka `acks=all`과 보장 수준이 다르다.

### ③ 소비 구간

```
❌ 받음 → ack → 처리     (처리 중 죽으면 유실)
✅ 받음 → 처리 → ack     (at-least-once)
```

**Kafka의 함정 — auto commit**
```yaml
enable.auto.commit: true      # 기본값. 5초마다 offset 자동 커밋
```
**처리와 무관하게 시간 기준으로 커밋된다.** 처리 안 된 것까지 "읽었다"고 표시될 수 있다.
→ 금융에서는 **`enable.auto.commit=false` + 처리 후 수동 커밋.**

### 유실 방어 체크리스트

| 구간 | Kafka | Redis Stream |
|---|---|---|
| 발행 | `acks=all` + **Outbox** | `XADD` 결과 확인 + Outbox |
| 브로커 | `replication.factor=3`, `min.insync.replicas=2` | AOF + 복제 (한계 있음) |
| 소비 | auto commit off + 처리 후 커밋 | 처리 후 `XACK` |
| 최종 | **대사 배치** | **대사 배치** |

> **마지막 줄이 진짜 답.** 아무리 막아도 분산 시스템은 틀어진다. **틀어진 걸 찾아내는 배치가 최종 안전망.**

## 5-2. 중복 (Duplicate)

```
소비자: 처리 완료 ✅ → ack 보내기 직전 💥 다운
브로커: ack 못 받음 → "아직 처리 안 됐네" → 재전달 → 두 번 처리
```
**at-least-once를 택한 이상 중복은 막을 수 없다.** 막는 게 아니라 **흡수**하는 것.

### 멱등성(Idempotency)

> **같은 요청을 몇 번 실행해도 결과가 같은 성질.**

```
❌ 멱등 아님:  잔액 = 잔액 - 1000     (실행할 때마다 줄어듦)
✅ 멱등:       잔액 = 5000            (몇 번 해도 5000)
✅ 멱등:       거래ID 중복이면 무시
```

### 구현 3가지

**① 멱등성 키 + 처리 이력 테이블** ← 가장 확실
```java
public void consume(RepaymentEvent e) {
    String key = e.getTransactionId();          // 금결원 거래고유번호
    if (!idempotencyRepo.tryInsert(key)) {      // UNIQUE 제약으로 원자적
        return;                                  // 이미 처리됨
    }
    알림톡_발송(e);
}
```
**핵심은 UNIQUE 제약.** `if (존재하나?) → 없으면 insert`는 **동시에 두 개가 들어오면 뚫린다.** DB의 UNIQUE 위반을 이용해야 원자적.

**② Redis + TTL** — `payment-settlement-core` 방식
```java
Boolean ok = redis.opsForValue().setIfAbsent("idem:" + key, "1", Duration.ofHours(24));
if (!ok) return;   // 이미 처리됨
```
`SETNX`는 원자적. TTL로 자동 정리되니 테이블이 안 부푼다.
**단, Redis가 유실되면 방어선이 사라진다** → 금액이 걸린 건 DB 테이블 병행.

**③ 상태 기반 (조건부 갱신)**
```sql
UPDATE repayment SET status = 'DONE'
 WHERE id = 57 AND status = 'PENDING'   -- 이미 DONE이면 0건 갱신
```
별도 테이블 없이 **업무 테이블 자체로 멱등성**을 만든다. 가장 가볍다.

### ★ 외부 API가 진짜 문제

```
소비자: 멱등성 체크 통과 → NH 이체 API 호출 → 성공 → 이력 기록 직전 💥
재시도: 이력이 없으니 통과 → NH 이체 API 또 호출 → 💸 이중 이체
```
**내 DB만 멱등해서는 부족하다. 외부 호출도 멱등해야 한다.**

**해법: 외부 API에 멱등성 키를 넘긴다.**
- Stripe: `Idempotency-Key` 헤더
- 토스페이먼츠: `orderId`
- **NH 오픈뱅킹: 금결원 거래고유번호** ← **내가 실제로 한 것**

> 💡 **면접에서 이 연결이 가장 강하다.**
> "소비자 멱등성은 내부 상태만으로는 부족하고, 되돌릴 수 없는 외부 호출까지 멱등해야 합니다. 저는 금융결제원 거래고유번호를 멱등성 키로 사용해 재시도 시 중복 이체를 차단했습니다."

## 5-3. 순서 (Ordering)

```
파티션 0: [입금 5만]  → 소비자A (느림)
파티션 1: [출금 3만]  → 소비자B (빠름)
→ 출금이 먼저 처리됨 → 잔액 부족 오류
```
**병렬 처리와 순서 보장은 근본적으로 충돌한다.** 순서를 완벽히 지키려면 소비자가 1개여야 하고, 그러면 처리량이 죽는다.

### 실무 해법 — 전역 순서를 포기하고 키 단위로

```
파티션 키 = 계좌번호 (또는 채권번호)
계좌A → 항상 파티션 2 → 항상 같은 소비자 → 순서 보장 ✅
계좌B → 항상 파티션 5 → 다른 소비자 (병렬 ✅)
계좌A와 계좌B 사이 순서는? → 상관없다
```
**"필요한 범위에서만 순서를 지킨다."**

| 시스템 | 순서 단위 |
|---|---|
| Kafka | 파티션 (파티션 키로 결정) |
| RabbitMQ | 큐 (단일 소비자일 때만) |
| SQS Standard | **보장 없음** |
| SQS FIFO | Message Group ID |
| Redis Stream | 스트림 (그룹 내 분배되면 깨짐) |

### 순서에 의존하지 않는 설계가 더 낫다

```
❌ 순서 의존:  이벤트 순서대로 잔액 증감
✅ 순서 무관:  버전/시퀀스를 담고 오래된 건 버림
              UPDATE ... WHERE version < :newVersion
✅ 순서 무관:  최종 상태를 통째로 담아 보냄 (증분이 아니라 스냅샷)
```

> 💡 "순서를 어떻게 보장하나요"에 파티션 키만 말하면 60점.
> **"순서 의존을 줄이는 설계를 먼저 봅니다"** 를 덧붙이면 90점.

### ⚠️ 파티션 키 함정 2개
1. **파티션 수를 바꾸면 키→파티션 매핑이 깨진다.** 계좌A가 다른 파티션으로 가며 순서가 뒤섞임 → 처음에 넉넉히
2. **키 쏠림(hot partition)** — 특정 계좌에 몰리면 그 파티션만 밀린다

## 5-4. 재처리 (Retry & Recovery)

### 실패의 두 종류를 구분해야 한다

| | 예 | 대응 |
|---|---|---|
| **일시적(transient)** | 네트워크 순단, 타임아웃, DB 락 대기 | **재시도하면 성공** |
| **영구적(permanent)** | 잘못된 데이터, 없는 계좌, 스키마 불일치 | **재시도해도 영원히 실패** |

**영구 실패를 무한 재시도하면 poison message가 되어 큐 전체를 막는다.**

### 재시도 정책
```
1차 실패 → 1초 후
2차 실패 → 2초 후     ← 지수 백오프
3차 실패 → 4초 후
4차 실패 → DLQ 격리 + 알림
```
**지수 백오프 이유**: 외부 API가 과부하로 죽었는데 즉시 재시도하면 **더 밀어버린다.** 회복 시간을 준다.
**+ 지터(jitter)**: 여러 소비자가 동시에 실패하면 재시도도 동시에 몰린다(thundering herd) → 랜덤 오차를 섞는다.

### DLQ (Dead Letter Queue)
```
[메인 큐] → 소비자 → 3회 실패 → [DLQ] → 알림 → 사람이 확인
```
**없으면**: 실패 메시지가 계속 재전달되며 정상 처리까지 방해.
**있으면**: 문제 건만 격리되고 나머지는 정상 흐름 유지.

| 시스템 | DLQ 방식 |
|---|---|
| RabbitMQ | `x-dead-letter-exchange` |
| SQS | Redrive Policy (`maxReceiveCount`) |
| Kafka | 기본 없음 → 별도 토픽으로 발행 (`DeadLetterPublishingRecoverer`) |
| Redis Stream | 기본 없음 → PEL 재시도 횟수 보고 별도 스트림으로 |

> **DLQ에 쌓인 걸 아무도 안 보면 DLQ가 아니라 쓰레기통이다.** 반드시 알림을 건다.

### 재처리 3단계 — 규모별
```
① 개별 재시도  : 소비자 안에서 백오프
② DLQ 재투입   : 원인 수정 후 DLQ → 메인 큐
③ 전체 replay  : offset 되감기 (Kafka / Redis Stream만 가능)
```
③은 블록 3의 "알림톡 1,800건 재발송" 사고 대응. **로그 계열의 결정적 이점.**

### ★ 최종 안전망 — 대사 배치
```
매일 새벽:
  DB의 상환 완료 건  vs  알림 발송 이력      → 누락분 보정
  우리 DB 이체 내역  vs  은행 거래 내역      → 불일치 리포트 + 보정
```
**여기까지 있어야 금융 시스템이다.**

> 💡 **가장 크게 먹히는 문장**
> "재시도와 DLQ로 대부분을 커버하지만, 분산 환경에서는 어떤 방어를 해도 불일치가 남는다고 봅니다. 그래서 **원본 데이터와 처리 결과를 비교하는 대사 배치를 최종 안전망으로 두는 것**이 필수라고 생각합니다."

## 5-5. 처리량 병목 (Throughput)

### "처리량이 늘어나면 어디부터 병목이 생기나요?"

**순서대로 답해야 한다.** 실제로 이 순서로 터진다.
```
① 소비자 처리 속도       ← 90%가 여기
② 파티션 수 (병렬도 상한)
③ 외부 의존 (DB · API)
④ 브로커 자체
```

### ① 소비자 처리 속도 — 대부분의 원인
**진단 지표: Consumer Lag**
```
Lag = 발행된 최신 offset - 소비자가 처리한 offset
Lag 계속 증가 → 소비 속도 < 발행 속도 → 곧 터짐
Lag 일정      → 균형
```
Redis Stream이면 `XPENDING` / `XINFO GROUPS`.

**대응 순서**
1. **소비자 인스턴스 증설** — 가장 쉬움. 단, **파티션 수까지만 유효**
2. **배치 소비** — 1건씩 말고 100건씩 묶어 처리, DB write는 bulk
3. **소비자 내부 최적화** — 느린 쿼리, 불필요한 외부 호출 제거
4. **무거운 작업 분리** — 소비자는 가볍게, 무거운 건 또 다른 큐로

### ② 파티션 수 = 병렬도의 천장
```
파티션 3개 + 소비자 5개(같은 그룹) → 3개만 일하고 2개는 논다
```
**파티션을 늘리면 순서 보장이 깨진다**(5-3 함정) → **처음에 넉넉히 잡는 게 정석.**

### ③ 외부 의존 — 진짜 천장
```
소비자를 10개로 늘림
→ DB 커넥션 풀이 10 → 커넥션 대기
→ 외부 API rate limit → 429 폭탄
```
> 💡 **커넥션 풀과 정확히 연결된다.** 소비자를 늘려도 DB 커넥션이 그대로면 `hikaricp_connections_pending`만 쌓인다.
> **"소비자를 늘리기 전에 그 뒤의 자원 상한을 먼저 본다."**

### ④ 브로커 자체 — 가장 마지막
- Kafka: 디스크 I/O, 네트워크. **웬만해선 여기까지 안 간다**
- **Redis Stream: 메모리가 먼저 찬다.** 단일 스레드라 CPU도 한계
- RabbitMQ: 메시지가 쌓이면 메모리 압박 → flow control로 발행자를 막음

### 배압(Backpressure)
```
Lag 급증 감지
 ├ 소비자 오토스케일 (파티션 수까지)
 ├ 발행 속도 제한 (throttling)
 ├ 우선순위 분리 (중요 이벤트는 별도 토픽)
 └ 임계치 알림 → 사람 개입
```

### 면접 답변
> "가장 먼저 보는 건 **Consumer Lag**입니다. Lag이 지속 증가하면 소비 속도가 발행 속도를 못 따라가는 상태입니다.
>
> 병목은 보통 **소비자 처리 속도**에서 먼저 생기고 소비자를 늘려 대응합니다. 다만 **파티션 수가 병렬도의 상한**이라 그 이상은 소용이 없습니다.
>
> 그다음 병목은 소비자가 아니라 **그 뒤의 자원**인 경우가 많습니다. 소비자를 늘리면 DB 커넥션 풀이나 외부 API rate limit이 먼저 걸립니다. 그래서 소비자를 늘리기 전에 뒷단의 상한을 먼저 확인해야 한다고 봅니다.
>
> 브로커 자체가 병목이 되는 건 마지막 단계인데, Redis Stream이라면 메모리가 먼저 찰 수 있어 이 순서가 앞당겨집니다."

## 5-6. 5대 주제 통합 요약

| 주제 | 핵심 원리 | 1차 방어 | 최종 안전망 |
|---|---|---|---|
| **유실** | 발행·브로커·소비 3구간 | acks=all, 복제, 처리 후 ack | **Outbox + 대사** |
| **중복** | at-least-once면 필연 | **멱등성 키** (외부 API까지) | UNIQUE 제약 |
| **순서** | 병렬과 충돌 | 파티션 키 | **순서 의존 자체를 줄이기** |
| **재처리** | 일시/영구 실패 구분 | 백오프 재시도 → DLQ | **replay + 대사** |
| **처리량** | 소비자→파티션→외부→브로커 | Lag 모니터링, 소비자 증설 | 배압·우선순위 분리 |

### 노트 전체를 관통하는 3문장
1. **유실과 중복은 동시에 못 없앤다.** at-least-once + 멱등성이 표준
2. **순서는 전역이 아니라 키 단위로 지킨다.** 필요한 범위만
3. **어떤 방어를 해도 분산 시스템은 틀어진다.** 대사 배치가 최종 안전망

### 종합 면접 답변 (마무리용)

> "비동기 메시징에서 가장 중요한 전제는 **유실과 중복을 동시에 없앨 수 없다**는 점이라고 봅니다. 실무에서는 at-least-once를 택하고 중복을 소비자 멱등성으로 흡수하는 게 표준이고, 저도 이 방향이 맞다고 생각합니다.
>
> 다만 멱등성을 내부 DB에만 두면 부족합니다. 되돌릴 수 없는 외부 호출까지 멱등해야 하고, 저는 실무에서 금융결제원 거래고유번호를 멱등성 키로 사용해 재시도 시 중복 이체를 차단했습니다.
>
> 순서는 전역 보장을 포기하고 계좌나 채권 같은 키 단위로만 지키되, 가능하면 순서 의존 자체를 줄이는 설계를 선호합니다.
>
> 그리고 어떤 방어를 해도 분산 환경에서는 불일치가 남기 때문에, **원본과 처리 결과를 비교하는 대사 배치를 최종 안전망으로 두어야 한다**고 봅니다."
