# Redis 분산락은 실제로 무엇을 막아 주는가

> 분산락은 **동시 진입을 제한하는 도구**지, 정합성을 보장하는 도구가 아니다.
> 최종 정합성은 **멱등성 키 + DB 제약조건 + 트랜잭션 설계**가 만든다.

---

## 1. 면접 답변 (30~60초 구어체)

분산락은 특정 critical section에 동시에 들어오는 요청을 제한하는 도구지, 정합성을 보장해 주는 건 아닙니다.
락이 TTL로 먼저 풀리거나, 락을 잡은 서버가 작업 도중 죽으면 같은 구간이 두 번 실행될 수 있습니다.

그래서 저는 외부 이체를 다룰 때 락 여부와 무관하게 **멱등성 키**를 먼저 잡았습니다.
금융결제원 표준 규칙에 따라 거래고유번호를 내부에서 생성해 금결원에 등록하고, 그 번호를 멱등성 키로 썼습니다.
중요한 건 **재시도할 때 키를 새로 만들지 않고 최초 생성한 키를 그대로 재사용**하도록 요청 레코드에 함께 저장한 것이고, 그래서 같은 요청이 두 번 들어와도 이체는 한 번만 반영됩니다.

정리하면 **락은 동시 진입을 줄여 충돌과 실패율을 낮추는 최적화**고,
**최종 정합성은 멱등성 키와 DB 제약조건이 보장한다**고 보고 설계합니다.

---

## 2. 락이 보장하는 것 / 보장하지 못하는 것

| | 내용 |
|---|---|
| **보장한다** | 정상 동작할 때, 같은 키에 대해 한 번에 하나의 요청만 critical section 진입 |
| 보장 못 한다 | TTL 만료 후 뒤늦게 돌아온 요청의 DB 수정 (lost update) |
| 보장 못 한다 | 락 획득 서버가 죽은 뒤 다른 서버가 같은 작업을 재실행 |
| 보장 못 한다 | 외부 API 호출이 이미 나간 뒤의 롤백 (되돌릴 수 없는 부수효과) |
| 보장 못 한다 | DB 트랜잭션 정합성 자체 — 락은 DB 밖에 있음 |

**핵심**: 락은 "보통은 한 번만 실행되게" 만들 뿐, "반드시 한 번만 반영되게"는 멱등성이 만든다.

---

## 3. 락이 깨지는 대표 시나리오

```
서버A: 락 획득 (TTL 10초)
서버A: 외부 API 호출 → 네트워크 지연 12초
       ↓ (10초 시점) 락 자동 만료
서버B: 락 획득 → 같은 작업 실행
서버A: 12초 뒤 응답 받고 DB UPDATE  ← B가 쓴 값을 덮어씀 (lost update)
서버A: 락 해제 → 실제로는 B의 락을 해제
```

여기서 나오는 두 가지 방어:
1. **락 해제 시 소유자 확인** — 락 값에 고유 토큰(UUID)을 넣고, 해제할 때 그 토큰이 내 것일 때만 삭제. Redis에서는 GET 후 DEL이 원자적이지 않으므로 Lua 스크립트로 한 번에 처리
2. **DB 레벨 방어** — 버전 컬럼(낙관적 락) 또는 조건부 UPDATE(`WHERE status = '처리중'`)로 늦게 도착한 쓰기를 거절

## 4. 꼬리질문 답안

### Redis 분산락과 DB 비관적 락의 차이
- **DB 비관적 락(`SELECT ... FOR UPDATE`)**: 단일 DB 안에서만 유효. 커넥션과 트랜잭션을 점유하므로 커넥션 풀 고갈·데드락 위험. 대신 DB가 직접 보장하므로 TTL 같은 불확실성이 없다.
- **Redis 분산락**: 여러 인스턴스·여러 서비스·여러 DB에 걸쳐 걸 수 있다. 대신 네트워크 지연·TTL 만료·Redis 장애라는 변수가 추가된다.
- 선택 기준: 락 범위가 **하나의 DB 안**이면 비관적 락이 단순하고 안전. 범위가 **프로세스 경계를 넘으면** 분산락이 필요.

### TTL은 어떻게 정하나
- 기준은 "작업 최대 소요 시간 + 여유"지만, **외부 API 호출이 들어가면 최대 시간을 확정할 수 없다.**
- 그래서 TTL을 늘려 맞추는 대신 두 가지로 간다: ① 외부 호출에 타임아웃을 걸어 상한을 만든다 ② TTL은 그 상한보다 넉넉히 잡되, **TTL이 틀려도 깨지지 않도록 멱등성 키로 보강**한다.
- 작업이 길면 lease 갱신(watchdog) 방식도 있지만, 갱신 실패 시 처리가 또 문제라 복잡도가 올라간다.

### 락을 획득한 서버가 작업 중 죽으면
- TTL 만료로 락은 자동 해제된다 — 데드락은 안 생긴다.
- 문제는 **작업이 어디까지 진행됐는지 모른다**는 것. 외부 이체가 나갔는지 안 나갔는지 모르는 상태가 된다.
- 해결은 락이 아니라 **작업 상태를 DB에 먼저 기록**하고(처리중 → 완료/실패), 재시작 시 그 상태를 보고 재개하거나 보상하는 설계.

### 락이 만료된 뒤 기존 요청이 뒤늦게 DB를 업데이트하면
- **lost update**. 나중에 들어온 정상 처리 결과가 덮어써진다.
- 방어: 버전 컬럼(낙관적 락), 상태 기반 조건부 UPDATE, 또는 유니크 제약으로 중복 삽입 자체를 거절.

### 분산락을 썼는데도 멱등성 키가 필요한 이유
- 락은 **실행 횟수**를 줄이고, 멱등성은 **반영 횟수**를 고정한다. 둘은 보장 대상이 다르다.
- 락이 없어도 멱등성만 있으면 정합성은 지켜진다(대신 충돌·실패가 늘어난다).
- 멱등성이 없으면 락이 아무리 정교해도 TTL·네트워크·재시도 한 번에 중복이 뚫린다.
- 그래서 우선순위는 **멱등성 키가 먼저, 락은 그 위의 최적화**.

## 5. 실무 적용 사례 (면접 카드 연결)

### NH 오픈뱅킹 대량 출금이체
- 건별 이체를 대량 출금이체 API(최대 500건/회)로 전환
- **거래고유번호를 멱등성 키로 사용** → 재시도 시 중복 이체 차단
- 키는 금융결제원 표준 규칙에 따라 **내부에서 생성한 뒤 금결원에 등록**하는 구조. 즉 키 생성 시점·저장 위치·재시도 시 재사용 여부가 전부 우리 설계 영역이었다
  - 구성: 표준 포맷 위에 **내부 식별자(상품 단위) + 일자 + 일련번호**를 조합해 생성
  - 생성 시점: 요청 건을 만들 때 한 번만 생성. 재시도 시 **새로 만들지 않고 기존 키를 재사용**해야 멱등성이 성립
  - 저장: 요청 레코드에 함께 저장해, 재시도 경로에서 같은 키를 다시 꺼내 쓰도록 함
  - 이 설계가 틀리면(재시도마다 키를 새로 발급) 멱등성은 이름만 남고 중복 이체가 뚫린다
  - **유일성 보장**: 조합 키 컬럼에 **유니크 제약**을 걸어 DB가 최종 방어선을 맡도록 했다. 앞자리에 들어가는 상품 단위 식별자 자체가 유니크라 채번 범위가 상품 단위로 쪼개지고, 뒤 일련번호는 그 안에서만 규칙적으로 증가한다
  - 그래서 일련번호 채번을 원자적으로 만드는 데 따로 힘을 쓰지 않았다 — 설령 같은 번호가 만들어져도 **insert 단계에서 유니크 제약에 걸려 거절**되기 때문. 방어선을 애플리케이션이 아니라 DB에 둔 선택
- 건별 응답·실패 사유로 부분 실패를 분리, 실패 건만 재처리

### 원리금수취권 양도양수 정합성 재설계
- 외부 의존성 4종에 실패 지점별 **보상 트랜잭션**과 롤백 시나리오 정의
- 되돌릴 수 없는 외부 호출은 락으로 막을 수 없으므로, "실행 전 상태 기록 → 실행 → 결과 기록" 순서와 보상 경로로 설계
- 도메인별 에러 코드 체계와 감사 로그로 어느 단계에서 끊겼는지 추적 가능하게
