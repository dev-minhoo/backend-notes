# 1일 백엔드 - 04 - Redis 멱등성 구현과 3중 방어

> 03에서 결론 낸 것: **락은 TTL 때문에 보장이 아니다. 최종 방어는 멱등성 + DB 제약이다.**
> 04는 그걸 실제로 만들고, 동시 요청 50개를 쏴서 결제가 1건만 생기는지 확인한 기록이다.

---

## 1. 왜 공부하나

결제 요청은 두 번 온다. 사용자가 버튼을 연타하고, 네트워크가 끊겨 클라이언트가 재시도하고, 서버가 여러 대면 같은 요청이 다른 서버로 들어간다.
돈이 걸린 시스템에서 "두 번 처리됨"은 버그가 아니라 사고다.

01~03은 개념이었다. 이번엔 **코드로 막고, 테스트로 증명**한다.

## 2. 어디에 도움되나

- 결제·이체·정산처럼 **되돌릴 수 없는 작업** 앞에 붙는 공통 패턴
- 면접 단골: "중복 결제 어떻게 막나요?", "분산락으로 충분한가요?", "Redis가 죽으면?"
- 실무 연결: 금결원 거래고유번호를 멱등성 키로 쓰고, 컬럼 유니크 제약을 최종 방어선으로 둔 것과 같은 구조다

## 3. 핵심 — 3중 방어

요청이 들어오면 세 겹을 차례로 통과한다.

| 단계 | 막는 것 | 방법 | 이게 없으면 |
|---|---|---|---|
| ① DB 조회 | 이미 **완료된** 결제의 재요청 | 멱등성 키로 조회 → 있으면 기존 결과 반환 | 완료된 결제가 다시 실행됨 |
| ② Redis 선점 | 지금 **처리 중인** 같은 요청 | `SET key token NX EX 30` | 동시 요청 둘 다 ①을 통과해 둘 다 실행 |
| ③ DB 유니크 제약 | ①②가 **모두 뚫린** 경우 | 멱등성 키 컬럼 UNIQUE | 락 만료·Redis 장애 시 중복 저장 |

### ② Redis 선점 — 왜 이렇게 쓰나

```
SET idem:{key} {uuid} NX EX 30
```

- `NX` : 키가 없을 때만 저장 → 먼저 온 한 명만 성공
- `EX 30` : 30초 뒤 자동 삭제 → 서버가 죽어도 락이 영원히 남지 않음
- 값에 **UUID(소유 토큰)** : "이 락은 내 것"이라는 표시

### 해제는 왜 Lua로 하나

그냥 `DEL` 하면 사고가 난다.

1. A가 락을 잡음 (30초)
2. A 작업이 길어져 30초 초과 → 락 자동 만료
3. B가 같은 키로 락을 잡음
4. A가 끝나고 `DEL` → **B의 락을 지워버림**

그래서 "내 토큰일 때만 지운다"를 한 번에(원자적으로) 해야 한다.

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end
```

`GET` 하고 비교하고 `DEL` 하는 걸 자바 코드에서 따로 하면, 그 사이에 다른 요청이 끼어든다. Lua 스크립트는 Redis 안에서 통째로 실행되니 끼어들 틈이 없다.

### ③ 왜 DB 제약이 마지막인가

②는 **최적화**다. 대부분의 중복을 DB까지 오기 전에 걸러준다.
하지만 위 2번 상황(락 만료)이나 Redis 장애가 나면 ②는 뚫린다.
그때 마지막으로 막는 건 DB의 유니크 제약뿐이다. 중복 INSERT는 MySQL이 **1062 에러**로 거부한다.

> 락은 확률을 낮추고, 제약은 사고를 막는다.

## 4. 테스트로 증명한 것 (JUnit)

| 테스트 | 결과 |
|---|---|
| 같은 멱등성 키로 두 번 저장 | 두 번째에서 MySQL 1062 에러 |
| 스레드 100개가 같은 키로 동시에 선점 | 성공 1, 실패 99 |
| 같은 결제를 동시 요청 50개 | **결제 1건, 외부 이체 호출 1회** |

동시성 테스트는 `ExecutorService` 스레드풀(선점 테스트 32개, 결제 테스트 16개)에 요청을 한꺼번에 던지고, `CountDownLatch`로 모든 작업이 끝날 때까지 기다린 뒤 결과를 센다. 순서대로 실행되면 경쟁이 안 생겨서 버그가 있어도 통과하므로, 반드시 여러 스레드로 동시에 때려야 한다.

> 더 엄격하게 하려면 시작용 latch를 하나 더 둬서 모든 스레드가 준비된 뒤 **같은 순간에 출발**시키는 방법이 있다. 지금 구조는 스레드풀이 작업을 집어가는 시점이 조금씩 달라서 경쟁 강도가 그보다 약하다. (다음 개선 후보)

## 5. 비용과 한계 (면접에서 물어봄)

- **매 요청 DB 조회 부하** : ①이 매번 DB를 친다. 트래픽이 크면 완료 결과를 캐시로 당기거나, ①을 빼고 ②의 실패 응답만으로 처리할 수 있다. 대신 "이미 완료"와 "처리 중"을 구분해서 응답하지 못한다. 클라이언트 재시도 정책에 따라 고른다.
- **TTL 30초의 근거** : 정상 처리 시간보다 충분히 길고, 장애 시 너무 오래 막히지 않는 값. 외부 이체가 30초를 넘길 수 있으면 늘리거나 갱신(watchdog)을 붙여야 한다.
- **Redis 장애** : ②가 통째로 사라져도 ①③이 남아 정합성은 지켜진다. 성능만 떨어진다.

## 6. 실무와의 연결

| 이 프로젝트 | 실무 |
|---|---|
| 멱등성 키 | 금결원 거래고유번호 |
| 재시도 시 같은 키 재사용 | 재전송 시 거래번호를 새로 만들지 않음 |
| DB 유니크 제약 | 거래번호 컬럼 유니크 제약 |
| Redis 선점 | (실무엔 없음 — 단일 서버라 필요 없었음. 서버가 늘면 여기가 먼저 깨진다) |

## 7. 01~04 한 줄로

| 화 | 발견 | 필요한 것 |
|---|---|---|
| 01 큐 | 메시지는 두 번 올 수 있다 | 멱등성 |
| 02 구조 | 서버가 늘면 같은 작업이 두 번 돈다 | 락 |
| 03 개념 | 락은 TTL 때문에 보장이 아니다 | 멱등성 + DB 제약 |
| 04 구현 | 동시 50요청 → 1건 | 3중 방어의 증명 |

**전부 "돈이 두 번 나가지 않게"라는 질문 하나에 대한 답.**
